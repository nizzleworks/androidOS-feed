# androidOS-feed

A machine-readable JSON feed of Android OS release and security-patch information, inspired by [SOFA](https://sofa.macadmins.io) for Apple platforms.

Google publishes Android version and patch data across several human-readable pages — the developer site, the AOSP security bulletins, Pixel update bulletins — but offers no single structured feed. This repo scrapes those sources daily and publishes one normalized JSON file.

## The feed

```
https://raw.githubusercontent.com/nizzleworks/androidOS-feed/main/android_feed.json
```

Public, no auth, no rate limit beyond GitHub's own. Updated daily; committed only when the data actually changes, so the commit history doubles as a dated record of when Android versions and patch levels moved.

## What's in it

| Field | Description |
|---|---|
| `latest_major` | Current Android major version |
| `supported_majors` | Versions still receiving security patches |
| `n_minus_2_floor` | Computed N-2 baseline, for compliance policies |
| `majors[]` | Per-version detail — see below |
| `bulletin` | Current month's security bulletin — see below |
| `kev` | CISA Known Exploited Vulnerability matches |
| `urgency` | `routine` / `elevated` / `urgent` |
| `history` | Rolling 12 months of SPL and CVE counts |
| `generated` | UTC timestamp of the run |

### `majors[]`

One object per Android major version:

- `version`, `tier` (`N`, `N-1`, `N-2`), `release_date`, `days_since_release`
- `latest_point_release` and its date
- `active_support_until`, `security_support_until`
- `receiving_patches` — if false, this version's patch level can never advance
- `cves_this_month`, `criticals_this_month`, `branches_in_bulletin` (QPR branches preserved, e.g. `16-qpr2`)

### `bulletin`

- `latest_spl`, `patch_levels`, `latest_spl_age_days` / `_months`
- `by_patch_level` — CVEs split between the `-01` and `-05` levels, which is the distinction most SPL policies turn on
- `by_severity`, `by_type` (RCE / EoP / ID / DoS), `by_component` (Qualcomm, MediaTek, Arm, Kernel, ...)
- `critical_rce_cves`
- `mainline_cves` — fixes delivered via Google Play system updates rather than an OTA
- `published`, `updated`, `revisions` — bulletins are frequently revised after publication

### `urgency`

Criticals appear in nearly every bulletin, so "has criticals" is not a useful alert. This field is:

- `urgent` — a CVE in this bulletin appears in CISA KEV (actively exploited)
- `elevated` — a Critical RCE is present
- `routine` — everything else

## Sources

| Source | Used for |
|---|---|
| [endoflife.date](https://endoflife.date/android) | Major versions, release dates, support and EOL windows |
| [AOSP Security Bulletins](https://source.android.com/docs/security/bulletin) | Patch levels, CVEs, severity, type, affected branches |
| [CISA KEV catalog](https://www.cisa.gov/known-exploited-vulnerabilities-catalog) | Active exploitation status |

## Running it yourself

```bash
pip install requests beautifulsoup4
python3 android_feed_v4.py
```

Writes `android_feed.json` to the working directory. If an existing `android_feed.json` is present, its `history` array is read and extended — so run it from a checkout rather than a clean directory if you want the trend to accumulate.

## Scheduling

The feed is generated by a scheduled job that runs the script, then commits and pushes if the output changed. A GitHub Actions workflow is included (`workflow_dispatch` only) as a manual fallback.

Note that GitHub's `schedule:` cron is best-effort — runs are queued against shared capacity and may be delayed or dropped, with no upcoming-run view and no log for a run that didn't happen. If reliable timing matters, run the script from a machine you control.

## Caveats

- **This is a scraper.** Google redesigns the bulletin pages occasionally. The script fails loudly rather than publishing empty values, and preserves version data if only the bulletin parse breaks (flagged as `bulletin_error` in the output).
- **Patch level is not the same as version.** A device can be on a current major version and months behind on security patches, or vice versa. The two fields answer different questions.
- **OEM lag is not modeled.** The feed reports what Google has released. What any given device can actually install depends on its manufacturer and carrier. Samsung publishes its own [SMR bulletin](https://security.samsungmobile.com/securityUpdate.smsb).
- **endoflife.date is community-maintained**, not an official Google source.
